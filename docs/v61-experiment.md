# MailGuard v61

Эксперимент направлен на 95% распознавания спама при FP не выше 0,01% среди обычных писем. Это критерий проверки, не заявленный результат.

К признакам v60 добавляется смысл текста: замороженный многоязычный MiniLM в ONNX, обучаемый классификатор и сходство с размеченными письмами из TRAIN. Слабая японская HAM-разметка имеет ограниченный вес и не используется как эталон для ближайших соседей.

TRAIN, SELECT и CAL сохраняют разделение семейств. SELECT отдельно выбирает модель; CAL определяет пороги. Пороги для CJK, латиницы и остальных письменностей учитывают обычные письма. Японский язык не получает отдельного порога без HAM. Калибровка и проверка используют одинаковый режим обработки по одному письму для устойчивости int8-модели.

Новый TEST — 122 уникальных семейства из октябрьского спам-архива, зафиксированного 13 октября 2026 года. Все прежние данные заблокированы. Здесь нет новой размеченной обычной почты: FP проверяются отдельно на прежних HAM-наборах и отмечаются как повторная проверка. Этот эксперимент не доказывает качество на письмах Святослава.

Как устроен код:

- `tools/prepare_v61_new_mail.py` — новые письма, исключение совпадений и фиксация хешей.
- `tools/v61_semantic.py` — смысловые признаки, выбор TRAIN и ближайшие соседи.
- `tools/prepare_v61_features.py` — подготовка только TRAIN/SELECT/CAL и проверка сохранённой v60.
- `tools/train_v61_semantic.py` — обучение, выбор, калибровка, фиксация модели, затем тесты.
- `tools/v61_runtime.py` — применение сохранённой модели без обучения.
- `Dockerfile.v61-check` и `tools/check_customer_mail.py` — отдельная локальная проверка `.eml` без сети.

Снижение порога v60 до 95% на уже просмотренных тестах потребовало бы 13 FP/313 HAM на майском наборе, 11/1 968 на тесте v59 и 113/24 017 на старой английской почте. Эти пороги вычислены только для диагностики и не применяются: [диагностика](../reports/v61-v60-error-diagnostic.json).
