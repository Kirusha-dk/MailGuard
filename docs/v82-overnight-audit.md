# Ночной аудит v82: 21 октября

Задача — установить, где v82 ошибается, прежде чем менять обучение. Первая сессия дала 2888 FP / 12201 HAM на SELECT при development-пороге около 98% recall. Это плохой результат; эти 98% подобраны на той же выборке и не подтверждают переносимость.

Текущее продолжение 500 → 1000 optimizer steps запущено в [run 39510603511](https://github.com/Kirusha-dk/MailGuard/actions/runs/39510603511). Аудит имеет общую очередь с обучением: `.github/workflows/v82-error-audit.yml` начнётся после завершения текущего расчёта. Он требует завершённый checkpoint не ранее 1000-го шага и совпадающий с ним отчёт, иначе останавливается с ошибкой. Исходное состояние 500 шагов зафиксировано по run 39332953339.

`tools/audit_v82_errors.py` не создаёт оптимизатор и не выполняет градиентных обновлений. Хеши обоих checkpoint проверяются до и после расчёта. Данные — только SELECT и до 10000 уже предъявленных модели TRAIN. Факт предъявления восстанавливается по epoch/cursor и прежнему порядку SHA256; выбор небольшой подвыборки не использует метки или оценки модели. CAL, старые 100000 и Nazario-2024 аудитор не читает. Прежний подготовщик публичного корпуса сохраняет прежние правила исключения пересечений.

В отчёте:

- FP/FN, recall и FPR по источникам, длине текста и применению окна начало/конец;
- результаты при зафиксированном development-пороге и заранее заданном 0.5, без подбора нового порога;
- наиболее уверенные FP и пропущенный спам: только канонические хеши и числовые признаки, без тем, отправителей, URL или текстов писем;
- сравнение SELECT по идентичностям между v82 на 500 шагах и текущей v82: какие FP исчезли/добавились и какие прежние TP потеряны/обретены;
- совпали ли повторно вычисленные TP/FP с исходным отчётом и сохранились ли хеши checkpoint.

Это сравнение двух экспериментальных v82 на development. Оно **не заменяет** проверку отсутствия потерь относительно стабильной v80 и не является независимым тестом качества. Автоматического изменения меток, порогов, весов модели или основной v80 нет. При несовпадении пересчитанных чисел это нужно расследовать, а не объявлять улучшением.

Маленький JSON публикуется в `reports/v82-audits/step-<step>-<checkpoint-prefix>.json`; оценки и идентичности без текстов сохраняются в отдельный Actions artifact. Основной artifact продолжения обучения аудит не перезаписывает. Изменение `research/v82/audit.json` запускает только диагностику, без повторных optimizer steps.

Проверки без нейросетевых зависимостей:

```bash
python -m unittest discover -s tests/python -p test_v82_audit.py -v
```

## Дополнение по готовому score cache

Первый аудит завершился успешно. Выявлен пробел отчёта: SELECT по источникам и длине был опубликован только для 1000 шагов; у 500 шагов сохранялись лишь суммарные и парные числа. Для завершения сравнения подготовлен `tools/summarize_v82_audit_cache.py`. Он читает оценки из **фиксированного** artifact run 39511734148 и проверяет соответствие исходному Git-отчёту, двум ежедневным отчётам, полным fingerprints TRAIN/SELECT, порядку идентичностей и меток, исходным групповым/парным числам и обоим log loss. Нейросеть, checkpoint и оптимизатор не загружаются; повторного inference нет. Тексты используются локально только для воспроизведения fingerprint и группировки длины; в результат не попадают.

В `audit.json` поля `cached_audit_run_id` и `retry` выбирают только этот короткий путь workflow. Artifact проверяется по сохранённому digest; cache miss не вызывает нового скачивания или обучения. Первоначальный аудит и его score cache сохраняются. Чтобы позднее выполнить полный аудит другого checkpoint, нужно явно убрать поля `cached_*` и обновить запрос; основную месячную программу это не меняет.

Дополнение вычисляет на SELECT максимальный скалярный порог текущей v82, сохраняющий **каждый** TP v82 на 500 шагах: минимум текущего score среди прежних TP. Такой порог показывает цену отсутствия индивидуальных потерь в FP. Он подобран по тем же development-меткам, не является независимой проверкой, не сравнивает с v80 и не включается в продукт. Это проверяемый диагностический эксперимент без изменения весов или меток.

При повторе обнаружено небольшое несовпадение baseline log loss: исходный `0.24933327071271927`, из cache `0.24933319292296136`, разница `-7.77897579129494e-08`; текущий log loss воспроизвёлся точно. Формула и исходная реализация проверены, но причина разницы пока не установлена. Допуск **не увеличен**: `1e-9`. При таком несовпадении инструмент сохраняет диагностический summary с `source_report_log_losses_reproduced=false` и `status=diagnostic_only_log_loss_replay_mismatch`, затем завершает шаг с ошибкой. Workflow сохраняет этот явно помеченный результат; его нельзя считать полностью прошедшим аудитом. Проверки corpus/checkpoint provenance, идентичностей и счётчиков остаются обязательными. Следующий отдельный read-only эксперимент — сравнить исходный `validate` (`no_grad`) и аудитор (`inference_mode`) на том же 500-step checkpoint и SELECT, сохранив числа и максимальное расхождение score. Гипотеза о численной разнице inference пока не подтверждена.

## Ограниченный replay двух inference-контекстов

`tools/check_v82_inference_replay.py` реализует этот эксперимент. Запрос `replay_inference_contexts=true` выбирает только job `compare-inference-contexts` с общей очередью кампании. Он восстанавливает фиксированные artifact исходного аудита и checkpoint500 run39332953339, строго проверяет **все** metadata, manifests, полный content fingerprint TRAIN/SELECT, порядок идентичностей/меток и SHA256 checkpoint. TRAIN читается только для fingerprint; scoring выполняется только на SELECT, двумя проходами batch32. CAL/test не открываются.

Первый проход вызывает исходную неизменённую функцию `v82_neural.validate` в `no_grad`; обёртка сохраняет её оценки, возвращая исходные logits. Второй использует прежний цикл аудитора в `inference_mode` на том же объекте модели, токенизаторе и входных batch. Сравниваются оценки по идентичностям, FP/TP при **сохранённом** пороге, log loss и старый cache. Проверяются неизменность всех параметров, RNG и файлов; оптимизатор не создаётся. Версии, CPU capability и настройки матричных операций записываются в числовой отчёт. Поля качества остаются false; успешное завершение эксперимента не означает воспроизведение исторического loss, если соответствующий флаг false.

Результат — `reports/v82-audits/step-500-inference-replay.json`; оценки без текстов — отдельный artifact. Старые диагностические отчёты сохраняются. При одинаковых результатах двух контекстов гипотеза о причине в `no_grad`/`inference_mode` считается не подтверждённой данным replay; исторический loss не объявляется совпавшим. Для последующего полного аудита нужно явно убрать `replay_inference_contexts` и `cached_*` из запроса. Месячное обучение, optimizer/RNG/cursor сохранённой кампании и стабильная v80 не изменяются.

Эксперимент [39530785619](https://github.com/Kirusha-dk/MailGuard/actions/runs/39530785619) завершился: на **всех 22790 SELECT** `no_grad`, `inference_mode` и прежний cache дали **полностью одинаковые score**, максимум разницы 0; TP10378 / FP2888 при сохранённом пороге. Оба контекста дали loss `0.24933319292296136`, поэтому расхождение со старым `0.24933327071271927` этим переключением **не объяснено**. Hash checkpoint, параметры модели, RNG и cache не изменились, optimizer steps 0. Зафиксировано CPU AVX2, 3 потока, PyTorch2.14.1+cpu, MKLDNN=true, precision=highest. Историческое окружение в исходном checkpoint не описано настолько подробно, чтобы по этому опыту установить причину различия; CPU/backend остаются гипотезой, не установленным фактом.

Общий helper парных сравнений первоначально подписал и этот replay как сравнение двух checkpoint. Исправлена только эта метка и добавлена проверка: здесь один checkpoint и его inference/cache. Числа не пересчитывались и не изменялись; исходный report/score cache остаётся в неизменном Actions artifact, а Git-отчёт содержит явную аннотацию исправления. Основной `paired_select` полного аудита по-прежнему сравнивает два разных v82 checkpoint.

Запрос помечен `execution_complete=true` с `completed_replay_run_id=39530785619`: изменения документации/метаданных не должны повторять тяжёлый расчёт. Следующий осмысленный запрос должен явно снять маркер завершения и изменить `retry`. Месячная программа не зависит от этого маркера.
