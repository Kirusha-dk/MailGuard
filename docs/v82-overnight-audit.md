# Ночной аудит v82: 21 октября

Задача — установить, где v82 ошибается, прежде чем менять обучение. Первая сессия дала 2888 FP / 12201 HAM на SELECT при development-пороге около 98% recall. Это плохой результат; эти 98% подобраны на той же выборке и не подтверждают переносимость.

Текущее продолжение 500 → 1000 optimizer steps запущено в [run 39510603511](https://github.com/Kirusha-dk/MailGuard/actions/runs/39510603511). Аудит имеет общую очередь с обучением: `.github/workflows/v82-error-audit.yml` начнётся после завершения текущего расчёта. Он требует завершённый checkpoint не ранее 1000-го шага и совпадающий с ним отчёт, иначе останавливается с ошибкой. Исходное состояние 500 шагов зафиксировано по run 39332953339.

`tools/audit_v82_errors.py` не создаёт оптимизатор и не выполняет градиентных обновлений. Хеши обоих checkpoint проверяются до и после расчёта. Данные — только SELECT и до 10000 уже предъявленных модели TRAIN. Факт предъявления восстанавливается по epoch/cursor и прежнему порядку SHA256; выбор небольшой подвыборки не использует метки или оценки модели. CAL, старые 100000 и Nazario-2024 аудитор не читает. Прежний подготовщик публичного корпуса сохраняет прежние правила исключения пересечений.

В отчёте:

- FP/FN, recall и FPR по источникам, длине текста и применению окна начало/конец;
- результаты при зафиксированном development-пороге и заранее заданном 0.5, без подбора нового порога;
- наиболее уверенные FP и пропущенный спам: только канонические хеши и числовые признаки, без тем, отправителей, URL или текстов писем;
- сравнение SELECT по идентичностям между v82 на 500 шагах и текущей v82: какие FP исчезли/добавились и какие прежние TP потеряны/обретены;
- совпали ли повторно вычисленные TP/FP с исходным отчётом и сохранились ли хеши checkpoint.

Это сравнение двух экспериментальных v82 на development. Оно **не заменяет** проверку отсутствия потерь относительно стабильной v80 и не является независимым тестом качества. Автоматического изменения меток, порогов, весов модели или основной v80 нет. При несовпадении пересчитанных чисел это нужно расследовать, а не объявлять улучшением.

Маленький JSON публикуется в `reports/v82-audits/step-<step>-<checkpoint-prefix>.json`; оценки и идентичности без текстов сохраняются в отдельный Actions artifact. Основной artifact продолжения обучения аудит не перезаписывает. Изменение `research/v82/audit.json` запускает только диагностику, без повторных optimizer steps.

Проверки без нейросетевых зависимостей:

```bash
python -m unittest discover -s tests/python -p test_v82_audit.py -v
```
