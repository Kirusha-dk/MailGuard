## Подтверждённые наблюдения на 1000 шагах

Большая часть FP — Merged-public: 1820 из 2326 (78.25%); FPR источника 1820 / 8646 = 21.05%. У GenSpam FPR 104 / 403 = 25.81%. Это описание концентрации ошибок, не доказательство неверных меток.

Очень короткие HAM (до 30 слов) имеют 440 FP / 874 = 50.34% на SELECT и 164 / 317 = 51.74% на уже наблюдавшемся TRAIN. Проблема видна в обоих разделах; объяснять её только переобучением нельзя. Для 201–500 слов на SELECT recall 2088 / 2184 = 95.60%; на эту группу приходится 96 из 211 FN. Группа `whole-text` означает отсутствие символьного окна 1200+600, но токенизатор всё равно может обрезать текст до 192 токенов. Причинная роль обрезки пока не измерена.

На label-blind подвыборке 10000 из 16000 наблюдавшихся TRAIN: 80 FN / 4683 SPAM, 888 FP / 5317 HAM, FPR 16.70%. SELECT FPR 19.06%. Состав источников различается: если стандартизовать TRAIN FPR по долям HAM-источников SELECT, получается 18.11%. Поэтому сырую разницу 16.70% → 19.06% нельзя целиком трактовать как переобучение. Стандартизация описательная, не причинная.

Предзаданный порог 0.5 дал на SELECT 566 FP, но recall только 89.87% (1073 FN). Простое повышение порога ухудшает обнаружение спама.

## Выполненный диагностический эксперимент: цена сохранения всех прежних TP

На зафиксированных score из cache вычислен **максимальный** скалярный порог текущей v82, сохраняющий каждый TP v82 на 500 шагах: минимум текущего score среди прежних TP, `0.003785335225984454`. При правиле `score >= threshold` получились **4120 FP / 12201 HAM**, 10501 TP, 88 FN; прежних TP потеряно 0, найдено ещё 123. Исчезли только 64 прежних FP, добавились 1296.

Следовательно, **на этих development-оценках одним скалярным порогом нельзя одновременно сохранить все TP 500-step v82 и уменьшить её 2888 FP**: даже максимальный допустимый порог даёт 4120 FP, а более низкий не уменьшит FP. Это установленное ограничение текущего ранжирования, не проверка относительно v80. Порог вычислен по development-меткам и не включается в продукт; 99.17% recall при нём не является независимым результатом. Неустановленная причина малого loss-расхождения также остаётся ограничением этого дополнительного разбора.

Для расследования replay запущен отдельный ограниченный [эксперимент 39530785619](https://github.com/Kirusha-dk/MailGuard/actions/runs/39530785619): восстановить фиксированный 500-step checkpoint с тем же SHA256 и frozen SELECT, сравнить исходный `validate` в `torch.no_grad()` с аудитором в `torch.inference_mode()`; проверить log loss, максимальное расхождение score и TP/FP по идентичностям. Скрипт строго проверяет все metadata, content fingerprints, исходный cache и состояние модели/RNG. Оптимизатор не создаётся, CAL/test не открываются. В момент этой записи результат ещё ожидается; это не новый запуск обучения. Допуск не ослаблен.

## Подготовленный следующий эксперимент по весам TRAIN

Проверена фактическая формула текущего loss и опубликованные **TRAIN**-счётчики: Merged-public содержит **22051 / 47683 = 46.24%** всех TRAIN HAM, но inverse source/class weights отводят ему **10.06%** суммарного веса HAM-loss. Общая нормировка на средний вес не меняет эти доли. Это подтверждённая особенность целевой функции; её причинное влияние на FP пока не измерено. [Числовой разбор](../v82-audits/train-ham-loss-allocation.json) не использует CAL/test или метки отдельных сообщений. Добавочный phishing-корпус содержит только SPAM и HAM-доли не меняет.

Подготовлен [протокол отдельного сравнения](../../research/v82/experiments/source-weighting-ablation.json): две независимые экспериментальные копии одного проверенного checkpoint500, одинаковые TRAIN-порядок, RNG, AdamW и 500 шагов; меняется только наличие обратных частот источников/классов, HAM cost остаётся 2. Контроль сохраняет текущие веса, кандидат убирает обратные частоты. Проверять FP и индивидуальные потери TP, не только общий recall. Новый fork должен иметь собственные metadata происхождения, артефакты и бюджет; обходить проверки месячной кампании нельзя. Протокол **подготовлен, не выполнен**; автоматического запуска нет, основной бюджет и веса не менялись. Улучшение от него не заявлено.

Проверки дополнения: **9 tests пройдены** локально и в Actions, включая реальный CLI на выдуманном cache, который сохраняет diagnostic с `false` и всё равно возвращает ошибку при loss-дрейфе. Перестановка идентичностей отвергается; тексты не сериализуются. YAML и общая очередь проверены. Эти проверки инженерные, не измерение качества на почте.

Месячный `cycle.json`, обучение, исходные optimizer/RNG/cursor и основной checkpoint не изменены. До появления подтверждённого результата ни увеличение штрафа HAM, ни новая архитектура не объявляются улучшением. Кандидат остаётся экспериментальным; критерий принятия сохраняется: снижение FP, ноль потерь индивидуальных TP относительно v80, затем независимая проверка на новых источниках.
