## Подтверждённые наблюдения на 1000 шагах

Большая часть FP — Merged-public: 1820 из 2326 (78.25%); FPR источника 1820 / 8646 = 21.05%. У GenSpam FPR 104 / 403 = 25.81%. Это описание концентрации ошибок, не доказательство неверных меток.

Очень короткие HAM (до 30 слов) имеют 440 FP / 874 = 50.34% на SELECT и 164 / 317 = 51.74% на уже наблюдавшемся TRAIN. Проблема видна в обоих разделах; объяснять её только переобучением нельзя. Для 201–500 слов на SELECT recall 2088 / 2184 = 95.60%; на эту группу приходится 96 из 211 FN. Группа `whole-text` означает отсутствие символьного окна 1200+600, но токенизатор всё равно может обрезать текст до 192 токенов. Причинная роль обрезки пока не измерена.

На label-blind подвыборке 10000 из 16000 наблюдавшихся TRAIN: 80 FN / 4683 SPAM, 888 FP / 5317 HAM, FPR 16.70%. SELECT FPR 19.06%. Состав источников различается: если стандартизовать TRAIN FPR по долям HAM-источников SELECT, получается 18.11%. Поэтому сырую разницу 16.70% → 19.06% нельзя целиком трактовать как переобучение. Стандартизация описательная, не причинная.

Предзаданный порог 0.5 дал на SELECT 566 FP, но recall только 89.87% (1073 FN). Простое повышение порога ухудшает обнаружение спама.

## Сделанное дополнение и следующий проверяемый расчёт

В исходном JSON не хватало разбивки **500 шагов** по источникам/длине, хотя исходные оценки сохранены. Добавлены `tools/summarize_v82_audit_cache.py` и отдельный короткий путь того же audit workflow. Запрос с `retry=2026-10-21-cached-breakdown-v1` использует фиксированный готовый artifact: модель, checkpoint и оптимизатор не открывает, inference/optimizer steps не выполняет. Проверяет manifests, полные fingerprints, порядок идентичностей/меток, исходные групповые/парные числа и оба log loss; при несовпадении останавливается.

Он также измерит цену сохранения каждого TP v82 на 500 шагах: максимальный допустимый порог текущей v82 — минимум её score среди прежних TP. Это один диагностический эксперимент по готовым оценкам; новый порог использует development-метки и не включается в продукт. Он не заменяет сравнение с v80. В момент записи этого раздела дополнение подготовлено, результат ещё не получен.

Проверки дополнения: 8 unit tests пройдены; реальный CLI на выдуманном маленьком cache создал summary без текстов и с нулём inference/optimizer steps, а перестановку идентичностей отклонил. YAML и общая очередь проверены. Эти проверки инженерные, не измерение качества на почте.

Месячный `cycle.json`, обучение, исходные optimizer/RNG/cursor и основной checkpoint не изменены. До появления подтверждённого результата ни увеличение штрафа HAM, ни новая архитектура не объявляются улучшением. Кандидат остаётся экспериментальным; критерий принятия сохраняется: снижение FP, ноль потерь индивидуальных TP относительно v80, затем независимая проверка на новых источниках.
